# SHACK-SERVER – Installation Guide

## 1. Overview
===============

SHACK-SERVER is a Node.js/TypeScript server for amateur radio operation with a REST API, WebSocket support, DX cluster connections, geo/QRZ enrichment and a web interface.

SHACK-SERVER can also integrate stations from DX Summit (`dxsummit.fi`) and HolyCluster (`holycluster.org`). The live spots show which DX clusters reported a station. From this the system calculates a score: the more independent clusters report the same station, the higher the score.

For SOTA and POTA activations a small triangle is shown next to the callsign – green for POTA and white for SOTA.

On request the application shows the spotted callsigns on a zoomable map. SHACK-SERVER also includes a simple logbook with ADIF import and ADIF export, and a contest console.

Transceivers are controlled via CAT: with built-in drivers (Yaesu FTDX10, Yaesu FTX-1, RGO-One, Icom CI-V, QRP Labs QMX) and via **Hamlib** for several hundred further models.

This guide describes the installation on a Raspberry Pi with:

- Debian GNU/Linux 13 (Trixie) / Raspberry Pi OS Lite (64-bit)
- ARM64 / `aarch64`
- Node.js 22
- npm 10
- PM2 7
- Project directory `~/SHACK-SERVER`

### Ports

| Port | Function |
|---|---|
| TCP 3000 | SHACK-SERVER web interface / REST API |
| TCP 8000 | built-in DX cluster telnet server |
| TCP 80 / 443 | Caddy (HTTPS), if set up |

In addition, the Raspberry Pi needs outgoing TCP connections to the configured DX cluster servers.

# Quick installation (recommended)

For most users a single command is enough. It sets up everything that the following chapters describe step by step.

**Requirements:** Raspberry Pi with **64-bit** Raspberry Pi OS (Debian 13), network, a user with `sudo` rights (see chapter 2).

As a normal user (not as root) in a terminal on the Raspberry Pi:

```bash
curl -fsSL https://raw.githubusercontent.com/cgraf63/SHACK-SERVER/main/scripts/install.sh | bash
```

The installer

1. checks the system (64-bit, memory, internet),
2. installs the system packages including **Hamlib** (for further transceivers) and **Node.js 22**,
3. installs **pm2** and sets up **autostart**,
4. gives the user access to the serial ports (group `dialout`),
5. downloads SHACK-SERVER from GitHub to `~/SHACK-SERVER` and builds it,
6. starts the setup assistant for `.env` / QRZ (`scripts/shack-server-setup`),
7. optionally sets up **Caddy** for **HTTPS in the home network** (`https://<IP>` and `https://<hostname>.local`) – optionally also a **public hostname behind Cloudflare**.

At the end it shows the address to open in the browser. Then set up the station and **Transceivers** in **Settings** (chapter 16).

If the user was newly added to the `dialout` group, reboot once (`sudo reboot`).

The installer's prompts are currently in German.

### Update

```bash
bash ~/SHACK-SERVER/scripts/install.sh --update
```

Fetches the latest version (`git pull`), builds it and restarts SHACK-SERVER. Local changes to files are detected; the installer then asks before overwriting anything.

### Important options

| Option | Effect |
|---|---|
| `--update` | Update only (no questions) |
| `--no-caddy` | Do not set up Caddy |
| `--dir DIR` | Different installation directory |
| `--repo URL` | Different repository address |
| `--dry-run` | Only show what would be done |

### Caddy and an existing configuration

A **self-maintained** `/etc/caddy/Caddyfile` is **never replaced without asking** (default: keep it). The installer then puts a suggestion into `~/SHACK-SERVER/Caddyfile.shack-server`.

A Caddyfile generated by the installer starts with the line `# SHACK-SERVER: managed by scripts/install.sh` and is rewritten on every run (backup first). To maintain it by hand, delete this first line.

**Security:** SHACK-SERVER has **no login of its own** and can control the transceiver, including PTT and the remote microphone. Public access must therefore only go through a protected path, e.g. **Cloudflare Tunnel with Cloudflare Access** (see chapter 18).

### Browser warning in the home network

In the home network Caddy issues its own certificate ("tls internal"). To stop the browser from warning, install the root certificate

```
/var/lib/caddy/.local/share/caddy/pki/authorities/local/root.crt
```

as trusted on your PC, tablet and phone. Tip: give the Raspberry Pi a **fixed IP** in your router.

The following chapters describe the manual installation step by step.

# 2. Requirements

You need:

- Raspberry Pi (recommended: Raspberry Pi 4 or 5) with a **64-bit** operating system
- Network connection
- SSH access
- User with `sudo` rights
- Access to the required external services (GitHub, DX clusters, QRZ)

### Recommended operating system

**Raspberry Pi OS Lite (64-bit)** is recommended for SHACK-SERVER.

A graphical desktop is not needed. SHACK-SERVER runs as a server service and is administered over the network or a web browser. The Lite version needs fewer resources and does not install unnecessary desktop components.

When writing the SD card with the **Raspberry Pi Imager** you can set directly:

- Hostname (e.g. `shack-server`)
- User and password
- Wi-Fi (if there is no network cable)
- **Enable SSH**

Recommended system check:

```bash
cat /etc/os-release
uname -m
```

Expected among other things:

```text
Debian GNU/Linux 13
aarch64
```

A 32-bit system (`armv7l`) is not supported – there are no Node.js 22 packages for it anymore.

```bash

```

Install the required base packages:

```bash
sudo apt install -y git curl ca-certificates gnupg build-essential netcat-openbsd libhamlib-utils avahi-daemon
```

| Package | Purpose |
|---|---|

| `avahi-daemon` | Reachable as `<hostname>.local` in the home network |

# 4. Install Node.js 22

SHACK-SERVER needs Node.js 22 or newer (`package.json`: `"engines": { "node": ">=22" }`). On Debian 13 ARM64, Node.js 22 is installed from NodeSource:

Check the version:

```text

npm 10.9.8
```

# 6. Access to the transceiver ports

Transceivers are connected via USB serial ports (`/dev/ttyUSB…`, `/dev/ttyACM…`). The user that runs SHACK-SERVER must be a member of the `dialout` group:

```bash
sudo usermod -aG dialout $USER
```

The change only takes effect after a **reboot** (or a new login):

```bash
sudo reboot
```

Check:

```bash
groups
```

`dialout` must appear in the output. Without this group the connection test in Settings reports "No permission for the serial port".

# 9. Basic configuration (.env)

`.env` now only holds **credentials and basic technical values**. Everything else (station, DX clusters, transceivers) is set in the web interface (chapter 10).

The easiest way to create `.env` is the setup assistant:

```bash
bash ~/SHACK-SERVER/scripts/shack-server-setup
```

It makes a backup first, asks for the port and the QRZ credentials (password and API key are not shown) and sets the file permissions.

The application loads `.env` via `import "dotenv/config";` in `src/app.ts` – so the file is not configured through PM2.

### Variables used

| Variable | Meaning | Required |
|---|---|---|
| `PORT` | HTTP port of SHACK-SERVER (default: `3000`) | no |
| `QRZ_USER` | QRZ.com username | for QRZ data |
| `QRZ_PASSWORD` | QRZ.com password | for QRZ data |
| `QRZ_API_KEY` | QRZ.com API key | for QRZ data |
| `CONTEST_CONTROL_KEY` | Key for protected contest management functions. Without this value these functions are locked. | no |

Example:

```env
PORT=3000

# QRZ
QRZ_USER=HB9xxx
QRZ_PASSWORD=xxxxxxxxxx
QRZ_API_KEY=xxxxxxxxxx

# Contest management (optional, choose freely)
CONTEST_CONTROL_KEY=a-long-random-value
```

The values shown are examples and must be replaced with your own.

**Note:** Earlier versions of this guide listed variables such as `SHACK_CALLSIGN`, `DXSPIDER1_…`, `HOLYCLUSTER_…` or `DXSUMMIT_…`. These are **no longer read** and can be removed from an existing `.env`.

### File permissions

Since `.env` contains credentials:

```bash
chmod 600 .env
```

Check:

```bash
ls -l .env
```

# 10. Where each setting lives

| What | Where | Edit with |
|---|---|---|
| QRZ credentials, port, contest key | `.env` | `scripts/shack-server-setup` or an editor |
| Callsign, operator, locator, club | `data/settings.json` | Web interface → **Settings** → Station |
| DXSpider, HolyCluster, DX Summit | `data/settings.json` | Web interface → **Settings** → DX Sources |
| Transceivers (driver, port, baud rate, Hamlib) | `data/radios.json` | Web interface → **Settings** → Transceivers |
| Logbook, contest data | `data/*.db` | Web interface |

The files under `data/` are created automatically on first start.

The files under `src/config/` (e.g. `settings.config.ts`, `radios.config.ts`) only contain **initial values for a new installation**. Changing them has no effect on an existing installation – the files under `data/` are what counts.

`.env` and `data/` do **not** belong in the repository (see chapter 11).

# 16. Set up transceivers

Transceivers are set up in the web interface – without editing files:

**Settings → Transceivers → + Add Transceiver**

1. Choose the **Transceiver / driver**:
   - built-in drivers: Yaesu FTDX10, Yaesu FTX-1, RGO-One, Icom CI-V, QRP Labs QMX
   - **Hamlib - other transceivers** for all other models (choose manufacturer and model from the list)
2. Choose the **Serial port**. Detected ports are shown with a readable name; for Yaesu radios with a CP2105 chip the CAT port ("Interface 0") is marked.
3. **Baud rate** – must match the CAT setting in the transceiver's menu. With Hamlib usually "Model default".
4. For Icom, also the **CI-V address**.
5. **Test connection** – on success shows the current frequency, otherwise the cause in plain words (radio off, no permission, wrong baud rate, port in use …).
6. **Save transceiver** – takes effect immediately, without a restart.

The transceiver reconnects automatically when it is switched on or the USB cable is plugged in again.

### Sharing the transceiver with other programs

A serial port can only be opened by one program at a time. If the transceiver should also be controlled by WSJT-X or a logging program, start a shared `rigctld` and in SHACK-SERVER choose the driver **Hamlib** with the connection **"Existing rigctld"** (host and port, default 4532).

### Check

```bash
cat ~/SHACK-SERVER/data/radios.json
curl -s http://localhost:3000/api/radios
```

Hamlib model list:

```bash
curl -s http://localhost:3000/api/radios/hamlib-models | head -c 300
```

# 18. Access from outside (optional)

SHACK-SERVER is meant for the home network. To use it on the road as well, you need protected access from the internet. Setting this up is up to the user and is not described step by step here. A proven approach is **Cloudflare Tunnel** together with **Cloudflare Access**.

### Important: security

SHACK-SERVER has **no login of its own**. Anyone who reaches the page can control the transceiver, including PTT and the remote microphone. Therefore:

- **No port forwarding** in the router to port 3000, 80 or 443.
- Only provide access through a tunnel that **always puts a login in front** – with Cloudflare an **Access policy** (e.g. login with an e-mail code, only for your own address).
- Create the Access policy **before** the first test and keep it active.

### How it works with Cloudflare

1. A domain on Cloudflare, a **tunnel** in the Zero Trust dashboard, and in it a **public hostname** (e.g. `shack.example.com`).
2. The tunnel connector `cloudflared` runs on the Raspberry Pi. When you create the tunnel, Cloudflare shows the matching command – either as a **Debian package** (system service) or as a **Docker container**. Both work; the Debian package does not need Docker. With Docker, add `--restart unless-stopped` so the tunnel comes back after a reboot.
3. Create an **Access application** with a suitable policy for the same hostname.

### How it fits with SHACK-SERVER

- **With Caddy:** the installer asks for the public hostname and adds its own `http://<hostname>` entry to the Caddyfile. In the tunnel, enter `http://localhost:80` as the target.
- **Without Caddy:** in the tunnel, enter `http://localhost:3000` directly as the target.
- If `cloudflared` runs in **Docker**, `localhost` means the container itself. Then start the container with `--network host`, or enter the Raspberry Pi's IP instead of `localhost`.

Cloudflare provides HTTPS towards the internet.

### Documentation

- Set up Cloudflare Tunnel: https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel
- Cloudflare Zero Trust (incl. Access): https://developers.cloudflare.com/cloudflare-one/

# 19. Check HTTP port 3000

On the Raspberry Pi:

```bash
sudo ss -lntp | grep ':3000'
```

A listener on port 3000 is expected.

Local test:

```bash
curl -s http://localhost:3000/api/diagnostics
```

If the server is running correctly, a JSON response is returned.

# 20. Check port 8000

SHACK-SERVER itself provides a DX cluster telnet server on port 8000.

Check:

```bash
sudo ss -lntp | grep ':8000'
```

Expected:

```text
0.0.0.0:8000
```

If needed, the port must also be reachable from the local network.

From another computer you can check, for example:

```bash
nc -vz <RASPBERRY-IP> 8000
```

---

# 21. Check DXSpider connections

The external DXSpider servers configured in Settings must be reachable from the Raspberry Pi.

Example:

```bash
nc -vz -w 5 <DXSPIDER-HOST> 8000
```

On the reference system both DXSpider connections are reachable via TCP/8000.

Important:

**Port 8000 has two different meanings here:**

1. SHACK-SERVER itself listens locally on TCP/8000.
2. SHACK-SERVER opens outgoing TCP connections to external DXSpider servers on their configured ports.

Both can be used at the same time.

# 24. Check QRZ

QRZ needs valid credentials in `.env`:

```env
QRZ_USER=...
QRZ_PASSWORD=...
QRZ_API_KEY=...
```

The application loads them via `dotenv`.

On a new Raspberry Pi, check first (shows only the names, not the values):

```bash
grep -o "^QRZ_[A-Z_]*" .env
```

Never publish the password or the API key in logs or screenshots.

If QRZ does not work, check the PM2 logs first:

```bash
pm2 logs shack-server --lines 100 --nostream
```

A callsign that is not on QRZ is **not a server error**. Not every callsign has to be on QRZ.

# 25. Firewall

If `ufw` or another firewall is used, the required ports must be opened.

Example for UFW:

```bash
sudo ufw allow 3000/tcp
sudo ufw allow 8000/tcp
```

With Caddy, also:

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

Then:

```bash
sudo ufw status
```

Outgoing connections to the external DX cluster servers must also be allowed.

# 30. Important notes

- `.env` contains confidential data and must not be published.
- QRZ credentials belong exclusively in `.env`.
- Station, DX clusters and transceivers are maintained in the web interface (**Settings**) and stored in `data/`.
- The anonymised values in this documentation must be replaced with the actual values of the respective site.
- Port 3000 is the web/API interface.
- Port 8000 is the built-in DX cluster telnet server.
- External DXSpider connections use the configured target address and target port.
- After changes under `src/`, `npm run build` is required, then the PM2 process must be restarted.
- SHACK-SERVER has no login of its own: access from the internet only via a protected path (e.g. Cloudflare Access), never via direct port forwarding.
